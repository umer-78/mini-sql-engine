# minisql: SQL engine over CSV files

[![CI](https://github.com/umer-78/mini-sql-engine/actions/workflows/ci.yml/badge.svg)](https://github.com/umer-78/mini-sql-engine/actions/workflows/ci.yml)

**Live demo:** https://umer-78.github.io/mini-sql-engine/

A small SQL engine, written from scratch in Python with no dependencies. It
tokenizes, parses and executes `SELECT` queries — joins, aggregates, grouping,
ordering, `UNION` and `CASE` — against ordinary CSV files, and can change them with
`INSERT`, `UPDATE` and `DELETE`.

```
$ minisql data -c "SELECT p.category, SUM(i.quantity * i.unit_price) AS revenue
                   FROM order_items i JOIN products p ON p.id = i.product_id
                   GROUP BY p.category ORDER BY revenue DESC"
+------------+---------+
| p.category | revenue |
+------------+---------+
| Displays   | 2433600 |
| Desk       | 2202000 |
| Audio      | 1260900 |
| Storage    | 783500  |
| Keyboards  | 434000  |
+------------+---------+
5 rows
```

No SQLite, no pandas, no parser generator. The tokenizer, the recursive-descent
parser, the expression evaluator and the execution model are all in
[`src/minisql/`](src/minisql), in about 1,200 statements of Python.

- **139 tests, 95% coverage**, Python 3.10–3.12
- Three-valued NULL logic, the way SQL actually defines it
- Errors point at the character that caused them

## Install and run

```bash
git clone https://github.com/umer-78/mini-sql-engine.git
cd mini-sql-engine
pip install -e ".[dev]"
pytest                          # 139 tests

minisql data                    # interactive shell over the sample data
minisql data -c "SELECT * FROM products LIMIT 3"
minisql data -f queries.sql --format csv
echo "SELECT COUNT(*) FROM orders;" | minisql data
```

The sample database in [`data/`](data) is four CSV files — customers, products,
orders and order items — regenerated by `python tools/make_data.py` from a fixed
seed, so the numbers in this README are reproducible.

## What it supports

```sql
SELECT [DISTINCT] col, expr AS alias, table.*, COUNT(*)
FROM table [alias]
[INNER | LEFT] JOIN other ON other.id = table.id
WHERE  cond AND cond OR NOT cond
       col = 1, <>, <, <=, >, >=
       col IS [NOT] NULL, col [NOT] IN (…), col [NOT] LIKE 'a%_'
       arithmetic: + - * / %
GROUP BY col [HAVING aggregate-condition]
ORDER BY col | alias | expr [ASC | DESC], …
LIMIT n OFFSET m

SELECT … UNION [ALL] SELECT …   [ORDER BY output-column | position] [LIMIT n]
CASE WHEN cond THEN x [WHEN …] [ELSE y] END,  CASE col WHEN 1 THEN x … END

INSERT INTO table [(col, …)] VALUES (…), (…)  |  INSERT INTO table [(col, …)] SELECT …
UPDATE table SET col = expr [, …] [WHERE cond]
DELETE FROM table [WHERE cond]
```

Aggregates: `COUNT(*)`, `COUNT(col)`, `COUNT(DISTINCT col)`, `SUM`, `AVG`,
`MIN`, `MAX`. The full grammar is in [docs/GRAMMAR.md](docs/GRAMMAR.md).

### Changing data

`INSERT`, `UPDATE` and `DELETE` change the tables in memory. Nothing touches your
CSV files until you ask: `.save` in the shell, or `--save` with `-c`/`-f`.

- **Types are checked.** A column keeps the type it was read with: `'eight'` will
  not go into a whole-number column, and a number will not go into a text column
  (the error suggests quoting it). An integer going into a decimal column is
  widened, as SQL does. A column with no values yet takes the type of the first one.
- **Each statement is all or nothing.** Every row is checked before any is
  written, so a bad value on the fifth `VALUES` row leaves the table unchanged.
- **`UPDATE` reads the old row.** `SET a = b, b = a` swaps the two columns,
  because every `SET` sees the row as it was before the statement.
- **`UNION` removes duplicate rows; `UNION ALL` keeps them.** `ORDER BY` and
  `LIMIT` after the last `SELECT` apply to the whole result, not the last branch.

```
$ minisql data --save -c "UPDATE products SET price = price + 500 WHERE category = 'Audio'"
+---------+
| updated |
+---------+
| 3       |
+---------+
1 row
saved products
```

## How a query runs

```
SQL text → tokenize() → parse() → Select (an immutable tree) → Engine.execute() → Result
```

1. **[`tokens.py`](src/minisql/tokens.py)** turns text into tokens, keeping each
   one's character offset so an error can point at it.
2. **[`parser.py`](src/minisql/parser.py)** is recursive descent. Precedence is
   the call chain, not a table: `_or` → `_and` → `_not` → `_comparison` →
   `_sum` → `_product` → `_unary` → `_primary`. Reading the functions top to
   bottom reads the precedence from loosest to tightest.
3. **[`ast.py`](src/minisql/ast.py)** holds frozen dataclasses. Once parsed,
   nothing rewrites the tree, so the plan that runs is the plan that was parsed.
4. **[`storage.py`](src/minisql/storage.py)** loads CSVs and infers a type per
   *column*, not per cell.
5. **[`executor.py`](src/minisql/executor.py)** builds the row stream from
   `FROM` and the joins, filters with `WHERE`, groups, filters groups with
   `HAVING`, projects, de-duplicates, sorts, then slices.

## Three details most toy engines get wrong

**NULL is unknown, not false.** `score > 0` where `score` is NULL is neither
true nor false, so the row is dropped by `WHERE` — and so is `score <= 0`:

```
$ minisql data -c "SELECT COUNT(*) AS all_rows, COUNT(city) AS with_city FROM customers"
+----------+-----------+
| all_rows | with_city |
+----------+-----------+
| 25       | 23        |
+----------+-----------+
1 row
```

`COUNT(*)` counts rows; `COUNT(col)` counts values. The two customers with no
recorded city are the difference. `false AND unknown` is still `false`, and
`true OR unknown` is still `true` — both are tested.

**A leading zero means it is not a number.** Type inference looks at every value
in a column, and a value like `04001` keeps the column as text, so a postcode
does not silently become `4001`.

**`ORDER BY` can name a column you did not select.** Each output row is kept
beside the input row it came from, so `SELECT name FROM people ORDER BY age`
sorts by age — rather than sorting by nothing, which is the quiet failure you
get if projection throws the source row away.

## Errors

A parse error shows the character it stopped at:

```
$ minisql data -c "SELECT name, city FROM customers WHERE city = 'Lahore' ORDER BY"
error: expected a value, found end of query
  SELECT name, city FROM customers WHERE city = 'Lahore' ORDER BY
                                                                 ^
```

A semantic error says what to do about it:

```
$ minisql data -c "SELECT city, name, COUNT(*) FROM customers GROUP BY city"
error: 'name' is not in GROUP BY and is not an aggregate — add it to GROUP BY or wrap it in one
```

Others in the same spirit: an unknown table lists the tables that do exist, an
ambiguous column names both tables it appears in, and an aggregate in `WHERE`
points you at `HAVING`.

## The shell

```
$ minisql data
minisql 1.1.0 — 4 table(s) loaded. '.help' for help.
sql> .tables
  customers         25 rows  5 columns
  order_items      153 rows  5 columns
  orders            60 rows  5 columns
  products          15 rows  5 columns
sql> .schema orders
  orders
    id               int
    customer_id      int
    placed_on        str
    status           str
    shipped_on       str
sql> SELECT c.name, COUNT(o.id) AS orders
...> FROM customers c LEFT JOIN orders o ON o.customer_id = c.id
...> GROUP BY c.name ORDER BY orders, c.name LIMIT 5;
+-----------------+--------+
| c.name          | orders |
+-----------------+--------+
| Maryam Chaudhry | 0      |
| Asad Raza       | 1      |
| Bilal Butt      | 1      |
| Hina Qureshi    | 1      |
| Iqra Chaudhry   | 1      |
+-----------------+--------+

```

`.format table|csv|json` switches the output and `.save` writes changed tables
back to their CSV files; leaving with unsaved changes prints a reminder. Piped
input goes through the same loop, so `echo '.tables' | minisql data` behaves
exactly like typing it.

## As a library

```python
from minisql import Database, run

db = Database.from_directory("data")
result = run("SELECT name, price FROM products WHERE price > 20000 ORDER BY price DESC", db)

result.columns        # ['name', 'price']
result.rows           # [['Standing desk', 92000], ['27" 1440p monitor', 68000], …]
result.dicts()        # [{'name': 'Standing desk', 'price': 92000}, …]
```

## Layout

```
src/minisql/tokens.py     tokenizer and the error type
src/minisql/parser.py     recursive-descent parser
src/minisql/ast.py        frozen node types
src/minisql/storage.py    CSV loading and type inference
src/minisql/executor.py   evaluation and execution
src/minisql/format.py     table, CSV and JSON output
src/minisql/cli.py        the `minisql` command and its shell
data/                     sample database (4 CSVs)
tools/make_data.py        regenerates data/ from a fixed seed
docs/GRAMMAR.md           the grammar, as the parser reads it
tests/                    139 tests
```

## Not supported

Subqueries, window functions, `RIGHT`/`FULL JOIN`, `CREATE`/`DROP TABLE`,
transactions across statements, indexes. Joins are nested-loop, so this is for files you can
hold in memory, not for a warehouse. What is here is meant to be correct and
readable rather than complete.
